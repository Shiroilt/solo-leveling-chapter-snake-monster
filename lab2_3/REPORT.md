## 2. What I changed in the glossary — [4]

The generated glossary is at `lab2_3/UBIQUITOUS_LANGUAGE.md`.

The agent's first pass included "Segment" and "Body" as separate terms, treating them as distinct domain concepts. I deleted "Segment" — it is an implementation detail (a `Point` in a `vector<Point>`), not a word anyone uses when talking about the game. "Body" was kept only in the Snake definition where it appears in the README, not as a standalone term.

The agent also initially listed "Collision" with a vague definition "when two things touch." I sharpened it to specify that collision is always snake-head-to-something (wall, own body, other body), and that it always ends the game immediately. The original phrasing would have applied to food-eating, which is not a collision.

The "Score" ambiguity — `getScore()` returning `max(score1, score2)` while display shows both separately — was missed by the agent's first pass. I added it to the Flagged Ambiguities section because it is a real design inconsistency with real consequences (the high-score file saves the top score, not per-player scores).

## 7. Analysis Q1–Q2 — [5]

**Q1 — Which smell did commit 3 fix?**

Commit 3 fixed **Shotgun Surgery** (S09 in `lab2_3/audits/lab1-head.md`): the concept "how many snakes exist" was written down in eight separate places — two pointer declarations in `GameBoard.h`, two score variables, two constructor `new Snake()` calls, two destructor `delete` calls, two `draw()` calls, two `clearTail()` calls, and the `Food::spawn()` signature taking `snake1Body, snake2Body` as separate parameters. Before the refactor, adding a third player meant editing all eight sites and risking inconsistency if any one was missed. After Commit 3, the only edit needed is changing `NUM_PLAYERS = 2` to `3` — one line. The `Food::spawn()` signature changed from a hardcoded pair to `vector<const vector<Point>*>`, so food spawning automatically excludes all snakes regardless of how many there are.

**Q2 — Compare commit 4 to Lab-1 diff. What changed in the cost?**

Lab 1's feature diff (`feat/multiplayer` vs `main`) touched 8 files, +766 / -692 lines. The changes were scattered across `Snake.h`, `Snake.cpp`, `Food.h`, `Food.cpp`, `GameBoard.h`, `GameBoard.cpp`, `GameManager.h`, and the compiled binary. A reviewer reading that diff had to mentally reconstruct the structural change (adding a second snake) interleaved with the feature logic (second player's controls, scoring, game-over messages) — they arrived as one undifferentiated blob.

Commit 4 touches 2 files, +51 / -78 lines, and the diff contains only feature-level decisions: what `PLAYER_CONFIG` entries mean for Player 2 (head color 11, body color 3, direction LEFT, spawn at 2/3 width), and how `displayGameInfo()` uses that table to print scores. A reviewer can read it in under a minute and ask a single focused question: "are these config values correct?" The structural question ("is a fixed-size array the right abstraction?") is fully answered in Commit 3, separately. The cost of understanding the feature went down. The cost of making mistakes went down too — there is no parallel duplicated block to forget to update.

## 8. Analysis Q3–Q4 — [5]

**Q3 — Did the Lab-1 assistant suggest restructuring before adding the feature?**

Reviewing `LLM-LOG.md`: the assistant's Prompt 1 response produced a `implementation_plan.md` that listed modifications across `Snake.h`, `Snake.cpp`, `Food.h`, `Food.cpp`, and `GameBoard.h/cpp`. The plan described _what_ to change per file but contained no mention of extracting a `Player` concept, consolidating snake storage, or naming the snake count in one place. The assistant went directly from "here is the existing code" to "here is what to add in each file," treating the design as fixed.

No restructuring was offered. The assistant did not suggest that `snake2` should be a second element in an array rather than a sibling pointer, or that `score2` should generalize `score1`. It offered the minimum diff to make the feature work.

What would have had to be different: the prompt would have needed to ask explicitly, for example: "Before implementing, identify any design problems in the existing code that would make this feature harder to add, and propose how to fix them first." Without that explicit instruction, an LLM assistant defaults to the feature as stated — it does not volunteer design critique unless asked.

**Q4 — How do you know commit 3 did not change behaviour?**

Honest answer: we do not know with certainty. There are no automated tests for this codebase. After the refactor, we compiled the code (0 errors), and the multiplayer executable ran and appeared to behave the same in a manual inspection: two snakes spawned at the expected positions, moved in response to their respective keys, ate food, and the collision detection ended the game correctly.

However, "played the game for a minute and it looked fine" does not constitute verification. Several scenarios were not tested: simultaneous collision (loser == 3), score reaching level-up threshold, food spawning with both snakes covering a large fraction of the board, and whether `getScore()` returning `max(scores[0], scores[1])` is exactly equivalent to the old `max(score1, score2)` in all edge cases (it is, but we confirmed this by code inspection rather than test).

To actually know, we would have needed: (a) a set of deterministic test cases with fixed random seeds covering each collision type, (b) a comparison of observable outputs before and after the refactor (e.g., game state snapshots at each tick for a scripted input sequence), or (c) a formal proof that the loop over `snakes[i]` with `1 - i` for other-collision is semantically equivalent to the original `snake1`/`snake2` cross-reference. None of those existed. The refactor was structurally conservative — no new logic was added — but "structurally conservative" is not the same as "provably equivalent."
